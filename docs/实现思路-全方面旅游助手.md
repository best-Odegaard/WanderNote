## 本地一键启动

根目录 `start-all.ps1`：按依赖顺序拉起后端(8080) → AI Agent(8002) → 前端(5173)，各服务跑在独立窗口里。

```powershell
.\start-all.ps1                    # 一键启动
.\start-all.ps1 -ApiKey sk-xxx     # 指定大模型 Key
.\start-all.ps1 -Rebuild           # 强制重打包后端
.\start-all.ps1 -CheckOnly         # 只体检，不启动
.\start-all.ps1 -Stop              # 停掉这三个服务（或直接跑 stop-all.ps1）
```

几个刻意的设计（都是踩过的坑）：

| 处理 | 原因 |
|---|---|
| **文件必须存为 UTF-8 with BOM** | 脚本所在路径含中文（`AI文旅`），且注释里有中文。存成无 BOM 的 UTF-8 时，Windows PowerShell 5.1 会按 GBK 解码，中文字节会吞掉换行，直接语法报错 |
| 弹窗命令只用**相对路径 + ASCII 窗口标题** | `Start-Process` 的命令串在 5.1 下受控制台编码影响，把中文路径拼进命令串有启动失败风险；中文目录交给 `-WorkingDirectory`（真参数，不走字符串解析）承载 |
| 端口占用**不报错退出**，改为沿用并补齐 | 本地常见场景是「Agent 和前端还开着，只想把后端拉起来」，此时应该只补缺的那个 |
| Agent 已在运行时**不再索要 MAAS_API_KEY** | 否则会为了一个已经在跑的服务卡住整个启动 |
| 后端**按需打包**（源码比 jar 新才打包） | `mvn package` 要 1 分半，每次都打包太慢；`-Rebuild` 可强制 |
| 前端地图 Key 为空时**只警告不阻断** | 没 Key 时定位与路线规划不可用，但其余功能照常，应该让用户先进得去 |

## 批次 2.12 实际落点

### ① 第一条消息紧贴导航栏

根因：`<scroll-view>` 上是内联 `:style="{ paddingTop: navHeight + 'px' }"`，
而 `navHeight` 只等于导航实际高度 —— **内联样式覆盖了 CSS 里的 `padding-top: 24rpx`**，
于是消息区恰好顶在导航底边，第一条消息和 AI 头像看着像被切掉。

修法：内联改成 `navHeight + 16`（间距只能加在内联里，CSS 那份已被覆盖）。

### ② 目的地选项与对话内容脱节

反馈场景：AI 推荐了成都/厦门/西安，紧接着问「你想去哪里？」，
选项却是固定的 广州/肇庆/重庆/成都/… —— 用户得自己在这堆里找那三个，对话上下文直接断了。

修法（放在后端，保持"槽位状态以后端为唯一事实来源"）：

| 步骤 | 做法 |
|---|---|
| 提取 | `SlotEngine.extractCityMentions(reply)`：用**识别词典**扫描本轮回复，按出现顺序取最多 3 个城市 |
| 记录 | `noteCityMentions(sessionId, cities)` 写进会话状态；**每轮覆盖**（不累积），排序跟着最新一轮走 |
| 排序 | `buildQuestion` 生成 `destination` 选项时，先放提到的城市，再补热门城市，全程去重 |
| 时序 | 必须在 `snapshot()` **之前**调用；且用**剥离候选块后的正文**（候选里的城市名不该影响排序） |

> 用识别词典而不是热门选项卡：AI 会推荐大理、泉州、景德镇这类不在选项卡里的城市，
> 它们同样该被排到前面，否则用户看到推荐却点不到。
> 实测这就暴露了词典的缺口 —— **景德镇、潮汕不在词典里**，于是又补了约 20 个
> 常被当作目的地的城市/古镇（婺源、平遥、敦煌、稻城、乌镇、宏村、阳朔…）。

### ③ 候选块漏到气泡里（显示层兜底）

现象：气泡正文里出现了 3 行候选问题。实测后端是**正确**的
（`reply` 不含标记、`suggested_questions` 正是模型给的那 3 条），属于页面在跑旧前端代码。

但借这个机会把防线补硬了 —— 之前只在**流式累积**这一条路径上截断，
而显示内容的来源不止一条：整包接口的 reply、刷新后从历史恢复的消息、
以及改动上线前就已存在的数据。现在在**渲染层**统一过滤一次（`displayText()`），覆盖全部路径。


## 批次 2.11 实际落点（候选与回答挂钩）

### 问题：候选与 AI 的回答没有联系

原来候选是纯规则的：按目的地命中 `city_zhaoqing` / `city_generic` 之类，产出
「深圳有什么必吃？」「两天怎么排不累？」——**和模型刚说的那段话毫无关系**。
用户看到的是一段具体回答 + 一组通用问题，接不上。

### 做法：让模型自己产出候选（零额外模型调用）

在 `chat_prompt.txt` 里约定：正文写完后必须附一个固定标记块。

```
<followups>
看海选哪段最方便？
南头古城怎么逛？
晚上去哪吃夜宵？
</followups>
```

| 环节 | 处理 |
|---|---|
| Agent | 直接透传，不解析（保持它"只转发模型输出"的定位） |
| Java `SuggestionEngine.extractFollowUps()` | 解析出候选 + **从正文里剥离标记块**；模型没给就返回空 |
| Java `ChatServiceImpl` | 候选优先用模型的，为空则**退回规则候选**（保证永远有东西可点） |
| 前端 `appendStreamText()` | 流式累积时按标记截断，气泡里不出现标记 |

**为什么要在 Java 侧剥离正文**（而不是只靠前端截断）：剥离后的正文要**入库**。
若把带标记的正文存进历史，下一轮作为历史回传给模型时，模型会以为自己上一轮就该带这么一段，
越滚越乱。所以剥离必须在组装 `assistantMsg` **之前**做。

**为什么前端截断要在"累积后的整串"上找标记**：流式是逐段到达的，标记本身可能被切成
`<foll` + `owups>` 两段，逐段匹配会漏。在整串上找天然安全，也不需要保留半截缓冲。

**效果对照**（同一次实测）：

| | 内容 |
|---|---|
| AI 回复 | 深圳适合"半海半城"地玩…🌊 看海优先选大梅沙、较场尾或深圳湾公园…🏙️ 南头古城、华侨城创意园…🍜 潮汕牛肉火锅… |
| 候选（本批） | **看海选哪段最方便？ / 南头古城怎么逛？ / 晚上去哪吃夜宵？** ← 3/3 条都紧扣回复里刚提到的内容 |
| 候选（原规则） | 深圳有什么必吃？ / 两天怎么排不累？ / 怎么去比较方便？ ← 与回复无关 |

### 顺带：prompt 热更新

`TravelAgent.__init__` 里缓存了 `chat_prompt`，导致**改文案必须重启进程**。
这个摩擦很坑：改完看不到变化，人会去别处找原因（为此浪费过好几轮）。
已改为 `build_chat_messages()` 里每轮重新读文件（几 KB 纯文本，开销可忽略）。

实测：临时往 prompt 追加一句「回复第一句必须以『热更新测试』开头」，**不重启 Agent** 直接调
`/api/chat` → 回复确实以此开头 ✓（之后已还原 prompt）。

> 注意：这次改动本身需要重启一次 Agent 才生效；**此后**再改 prompt 就不用重启了。

### 验证脚本的相关性检查

候选不再必然含城市名（模型会换说法），所以 `verify-e2e.ps1` 里原来那句
「候选里必须出现深圳」已不成立。改为**二字片段重合度**做近似判断：有重合词 → 认为相关；
判不准时只给 WARN，并把回复全文与候选都打出来供人眼确认 —— 避免测试给出误导性的红/绿。


## 批次 2.10 实际落点（真实链路首次跑通）

前面几批的验收一直卡在「看不到真实链路」，本批把环境问题全部挖掉，端到端验证通过 **15/15**。

### 三个"看起来像代码问题"的环境/基础设施 bug

**① 前端根本没连后端：`.env.development.local` 里 `VITE_USE_MOCK=true`**

后果被严重低估：mock 返回的是 `api/trip.ts` 里**写死的回复文案**，而且不带 `slot_state` /
`suggested_questions`，于是界面上既没有可选项也没有「猜你想问」，看起来完全像"AI 不理会我说的话"。
但 prompt 人设、槽位引擎、猜你想问其实一个都没跑到。

一条命令即可定性：

```powershell
curl.exe -sS "http://localhost:5173/src/utils/constant.ts"   # 看 VITE_USE_MOCK
```

已改回 `false`，并在 `ChatPlanner` 顶部加了 **Mock 告警条**（黄底），以后误开一眼可见。

> 教训：**为了"少弹一次网络错误"而打开全局 mock，代价是整条 AI 链路变成假的、且没有任何视觉提示。**
> 宁可弹一次真实错误，也不要用假数据把问题盖住。

**② `start-all.ps1` 启动 Agent 的那个窗口从不执行命令**

`Start-Process powershell -ArgumentList @('-NoExit','-Command',$inner)` 有两个叠加的坑：

- `-ArgumentList` 会被**用空格拼成一条命令行再重新解析**，命令串里的单引号被吞掉。
  Agent 那条命令恰好带引号（窗口标题与 key），于是解析失败 → python 根本没跑。
  后端/前端命令不含引号，所以一直正常，把这个 bug 掩盖了很久。
  修法：改用 **`-EncodedCommand`**（UTF-16LE 的 Base64），彻底绕开命令行解析与编码问题。
- **窗口样式必须显式指定**。实测同一台机器：有交互控制台时不指定也能执行；
  **无交互控制台**（被其它程序拉起的 shell）时，不指定 / `Normal` 会**一条命令都不执行**，
  而 `Minimized` / `Hidden` 正常。症状极具迷惑性：窗口进程建出来了，里面 java/node/python 一个都没起。
  修法：按 `[Console]::WindowWidth` 是否可用判断，自动在 `Normal` / `Minimized` 之间降级。

另外给每个服务窗口加了 `Start-Transcript`：**窗口里照常显示日志，同时落盘到 `logs/*.log`**。
这次排查最大的障碍就是"看不到窗口里的报错"，只能靠猜。

**③ 智能体启动失败的两层原因**

- 8002 被一个 2.5 小时前的旧进程占着（新进程报 `WinError 10048`）
- `MAAS_API_KEY` 既不在环境变量、也没有 `.env.local` / 也没有硬编码，于是启动即抛
  `RuntimeError: 未检测到环境变量 MAAS_API_KEY`

同时确认了一个诊断事实：**`Premature EOF` 不代表任何具体原因**。
Agent 在流式响应开始后抛异常就会掐断连接，Java 只看到"连接提前关闭"。
实测对照：Agent 没起 → `Connection refused`；Agent 起了但 key 无效 → `Premature EOF`。
真实原因（`401 Incorrect API key`）只出现在 **Agent 自己的日志**里。

### 批次 2.9 实际落点

#### ⚠️ 本批次最重要的一条：前端一直跑在 mock 模式

用户反馈"AI 回复很固定、不理会我说的话"，最后定位到**不是模型的问题，是压根没连后端**：
`frontend/.env.development.local` 里 `VITE_USE_MOCK=true`（当初为了"后端没起时首页不弹网络异常"而改的）。

后果比想象中大：那条回复是 `api/trip.ts` 里**写死的 mock 文案**，而且 mock 响应不带
`slot_state` / `suggested_questions`，所以界面上**既没有可选项、也没有「猜你想问」**。
前面几批做的 prompt 人设、槽位引擎、猜你想问，用户一个都没看到。

**验证方法（一条命令就能定性）**：

```powershell
curl.exe -sS "http://localhost:5173/src/utils/constant.ts"
# 看输出里的 VITE_USE_MOCK 是 "true" 还是 "false"
```

**已做的两件事**：
1. `.env.development.local` 改回 `VITE_USE_MOCK=false`（改了 `.env` 必须重启 dev server 才生效）；
2. `ChatPlanner` 顶部加了一条 **Mock 模式告警条**（`v-if="useMock"`，黄底），
   以后只要误开 mock，界面上直接写着"当前是本地 Mock 数据：AI 回复与行程都是假的"，不会再被误当成真实回复。

> 教训：**"为了少弹一次网络错误"而打开全局 mock，代价是整条 AI 链路都变成假的，且没有任何视觉提示。**
> 宁可弹一次真实错误，也不要用假数据把问题盖住。

#### 城市识别：词典与选项卡必须分开

`hotCities` 原本同时承担两个角色，而这两者诉求冲突：

| 用途 | 诉求 |
|---|---|
| 「你想去哪里？」的选项卡 | 要**少**（十几个才挑得动） |
| 从"我想去深圳"这类句子里识别城市 | 要**多**（不在表里就认不出来） |

只当选项卡用 12 个城市，用户说"去深圳"就什么都推不出来，后面所有依赖目的地的规则
（当地话题、猜你想问）整条失效 —— 界面看起来像"AI 没听懂"。

改法：`hotCities` 继续当选项卡；新增 `cityDictionary` 当**额外**识别词典；
两者在 `QuestionTree` 里取**并集**。

> 这里踩了一个坑：第一版把 `cityDictionary` 写成"完整的词典"，解析时**替换**掉了 hotCities，
> 结果热门城市（肇庆/广州…）反而从词典里消失，`想去肇庆` 认不出来。
> 单元测试直接把它抓出来了。所以现在是并集 —— 否则每新增一个热门城市都得记得写两处，
> 正是这次要消灭的那类坑。

#### 「猜你想问」的通用城市规则

原来只有 6 个手写城市规则，深圳这类没覆盖到的城市，推荐出来的问题跟目的地毫无关系。
新增 `city_generic` 规则（`whenDestinationKnown: true`）+ **`{city}` 占位符**，
任何城市都能得到当地相关问题，以后加城市不用再改配置。

#### 精细设置与对话联动（`pages/plan/wizard.vue`）

| 行为 | 改动 |
|---|---|

**测试暴露并修掉的两个设计缺陷**（都是"跑起来才发现"的类型）

1. **一条规则占满全部名额**。初版不限制每条规则贡献几条，结果 `missing_days` 一条就把 3 个名额用完，
   用户看到的全是"玩几天"的三种说法，城市/同行人这些**更具体**的建议永远轮不到。
   修法有两处，缺一不可：给规则加 `maxPerRule: 1`；同时把规则顺序改成**越具体越靠前**
   （city_* → with_family → budget → missing_* → round → generic）。
2. **兜底只给得出 1 条**。兜底原本是 1 条带 4 个问题的规则，`maxPerRule=1` 之后只能出 1 条 ——
   用户把信息给全、又没有城市规则命中时，屏幕上只剩 1 个候选。修法：把兜底拆成 4 条独立规则。

**「每轮被弹回登录页」的处理**

前置事实（都实测过）：CORS 预检正常（`Allow-Headers: authentication`）；带 token 打流式端点 200、不带 401；
`/travel/chat` 在 agent 挂掉时返回的是 `code:0` 业务错误（HTTP 200），**不会**触发跳登录；
`logout()` 只在「我的」页由用户手动触发；线上服务器的流式端点是 404（不是 401）。

因此唯一可能**因本次改动而新增**的跳登录来源，是流式客户端自己那个 401 分支。已改为：
**流式层不做鉴权决策，401 时直接抛错交给回落后的整包链路统一处理**。
理由：流式端点比普通接口多一层不确定性（网关/代理/端点未部署都可能 401），
在那里直接 `redirectToLogin()` 会让用户在"其实还能正常用"的情况下被反复弹回登录页。

同时在 `request.ts` 的 401 分支加了一行诊断日志（打印 url 与"本次是否带了令牌"），
因为"带令牌仍 401"（令牌被拒）与"没带令牌"（没存住）的修法完全不同，只打一句"请先登录"没法排查。

**流式链路的分层**（为什么不直接改 `/travel/chat`）

| 端 | 能力 | 走哪条路 |
|---|---|---|
| H5 / App | `fetch` + `ReadableStream` | 流式端点 |
| 微信小程序 | `uni.request` 不支持流式读取 | 自动回落整包端点 |

保留整包端点还有第二个理由：流式与整包的失败模式不同（半截气泡 vs 整体失败），
混在一个端点里前端很难处理。前端 `tryStreamChat()` 一旦失败会**清掉半截气泡**再走整包。

**踩到并已修复的两个坑（都很隐蔽）**

1. **SSE 里的中文被写成 `?`**。字符集对齐后定位到是写出阶段按非 UTF-8 落笔。
   最终做法不是继续调字符集，而是把事件载荷做成**纯 ASCII**（`toAsciiJson()` 把所有非 ASCII
   转成反斜杠-u 转义），前端 `JSON.parse` 还原。这样无论消息转换器 / 代理 / 容器按什么字符集落笔，
   字节都安全。实测：响应体**非 ASCII 字节数 = 0**，且 `delta` 拼接与 `done.reply` 均与源文本逐字相等。
2. **Java 注释里不能出现那个 Unicode 转义序列**。Java 在词法分析**之前**就处理 Unicode 转义，
   写在注释里同样会被当非法转义而编译失败（报错还指到文件第 4 行，极具误导性）。

**流式的验证方式**（不依赖大模型额度与用户的 API Key）

用 Python 起一个每 250ms 吐一段的流式桩服务，把测试实例的 `agent.chat-url` 指过去：
`java -jar ... --server.port=8081 --agent.chat-url=http://127.0.0.1:8999/stream`
然后带 token 打 `/travel/chat/stream`，实测 `event:delta` 在 **278 / 493 / 744 / 995 / 1246 / 1500 / 1750 ms**
依次到达（与桩的 250ms 节奏一致），`event:done` 在 2128ms 带完整 `slot_state`。
这同时证明了 `AgentHttpUtil.streamChat` 用字符块读（而非 `readLine()`）确实能逐段拿到数据 ——
按行读会把内容攒到第一个换行才返回，流式就名存实亡。

|---|---|
| 高德 URI `via` **最多 1 个途经点**，且仅驾车模式 | 不能做「一次性导入全天」，必须分段接续 |
| 腾讯 WebService 驾车支持 `waypoints`（分号分隔） | 应用内自绘全天路线可行；**上限需以官方文档为准**，实现上按段请求规避 |
| 携程无公开 API | 只能深链跳转 + 自建候选库 |
| 12306 无官方公开 API | 只能跳转购买；班次数据需授权数据源 |

## 7. 功能点 6：完整路线生成 + 导航（技术难点）

### 7.1 全天闭环路线计算

**现有能力**：`geo.ts:221` `planDrivingRoute(points)` 一次请求算 `from → waypoints → to`。
**缺口**：一次请求只能拿到**一整条 polyline**，**拿不到每一段的耗时/距离**，而产品要「第 2/5 段 · 下一站：七星岩」。

**方案：新增分段计算**

```ts
// frontend/src/utils/geo.ts 新增
export interface RouteSegment { from: LatLng; to: LatLng; path: RoutePoint[]; duration: number; distance: number }

/**
 * 分段规划：对相邻两点逐段请求，返回每段路径与耗时。
 * - 并发上限 3，避免触发腾讯 QPS 限制
 * - 任一段失败 → 该段降级为直线（path = [from, to]），duration/distance = null
 */
export async function planRouteSegments(points: LatLng[], concurrency = 3): Promise<RouteSegment[]>
```

复用现有 `planDrivingRoute([a, b])` 即可实现单段（只传两个点），再包一层并发调度 + 结果拼接。

**为什么不一次传全部途经点**：
- 拿不到分段耗时；
- 存在 `waypoints` 数量上限（**官方上限需查证**）；
- 单点失败会拖垮整条路线。

**渲染**：`TripMap` 已支持 `routeGroups`（多组、每组独立颜色、`path` 有则画沿路、否则直线，`TripMap.vue:328-346`）。一天一组颜色即可，**无需改 TripMap**。

### 7.2 起终点闭环

```
每日 points = [酒店] + [当天各节点按时间排序] + [酒店]
```

- 酒店坐标来自 `trip_hotel`；
- 若用户未选酒店 → 用「当天第一个景点」作为起点，并在 UI 提示「未设置住宿，已从首个景点出发」；
- 时间轴上的到达/离开时间由「上一段 duration + 停留时长」推算，**停留时长默认值**：景点 120min / 餐饮 60min / 体验 90min，可在编辑页调整。

### 7.3 导航唤起（分段接续）

**扩展 `map.ts`**：

```ts
// 1) 高德：补 from / via（URI 只支持 1 个 via，所以整条路线仍走分段）
buildAmapNaviUrl({ fromLng, fromLat, fromName, toLng, toLat, toName, mode })

// 2) 新增百度
buildBaiduNaviUrl({ fromName, toName })   // baidumap://map/direction?origin=&destination=&mode=driving
buildBaiduWebUrl(...)                     // 无 App 时 http://api.map.baidu.com/direction?...

// 3) 统一入口

```

**接续状态机**（`pages/trip/route.vue`）：

```

[第 2/5 段] 下一站：七星岩
[ 🧭 导航 ]  [ 上一段 ] [ 下一段 ] [ 跳过此点 ]
     ↓ openNavi(segments[i], provider)
外部地图接管 → 用户返回 → onShow 检测 → 提示「已到七星岩？进入下一段」
```

**调起失败探测**（关键，否则用户点了没反应也没提示）：

```ts
function openWithFallback(url: string, webFallback: string) {
  const t = Date.now()
  location.href = url                      // 或 plus.runtime.openURL
  setTimeout(() => {
    if (Date.now() - t < 1500 && !document.hidden) {
      window.open(webFallback, '_blank')   // 未安装 App → 降级网页版
    }
  }, 1500)
}
```

`document.hidden` 用于判断「App 是否被唤起（页面切到后台）」。微信内置浏览器无法调起 App，直接走网页版。

- 现有 `showNaviOptions`（`map.ts:156`）只有 3 项且无百度 → 扩展为 4 项。

### 7.5 性能与缓存
- 全天路线含 geocode + N 段 direction，**首算约 1-3 秒**；
- 建议：结果写 `trip_route_segment`（后端）或本地 `storage`（前端），**行程未变则不重算**；
- `geo.ts` 已有 `geoCache`（内存），可再加持久层缓存。

## 8. 功能点 7：火车票（12306）

### 8.1 分层设计（关键：数据源可插拔）

```
TransportService (interface)
├── StaticTimetableProvider    // 本地静态时刻表（P1 先上，覆盖主要线路）
├── ThirdPartyApiProvider      // 授权数据源（待商务，实现同接口）
└── NoopProvider               // 兜底：available=false
```

新增 `trip_transport`（Flyway `V2.7`）存快照。

### 8.2 接口

```
GET /transport/trains?from=&to=&date=
→ {
    "available": true,
    "source": "static-timetable",
    "trains": [{ "trainNo":"C7001", "departTime":"07:12", "arriveTime":"07:47",
                 "duration":35, "seatRefPrice":26, "fromStation":"广州南", "toStation":"肇庆东" }],
    "purchaseUrl": "…",            // 12306 或携程火车票
    "disclaimer": "时刻与价格以 12306 为准"
  }
```

`available=false` 时前端**降级为**：

```
┌──────────────────────────────────┐
│ 🚂 查 12-20 广州南 → 肇庆东 车票  │
│ [ 去 12306 购买 → ]               │
└──────────────────────────────────┘
```

**降级路径必须实现且默认可用**——否则数据源未就绪时整块功能不可用。

### 8.3 合规红线（不可妥协）

| 红线 | 要求 |
|---|---|
| 不代购 | 只跳转，不代下单、不代支付 |
| 不存账号 | **绝不采集/存储用户 12306 账号密码** |
| 不承诺实时 | 所有班次/价格标注「以 12306 为准」 |
| 数据授权 | 若展示班次，必须持有数据源授权凭证；否则只用静态时刻表或纯跳转 |

### 8.4 跳转实现
- 12306 官方 H5 查询页 URL 支持站名/日期参数（如 `kyfw.12306.cn/otn/leftTicket/init?fs=&ts=&date=`）；
- **该 URL 格式非官方承诺，随时可能变** → 封装 `build12306Url()`，并做「参数化失败则退化为官网首页」的兜底；
- 备选：跳携程火车票（深链参数同样需实测）。
