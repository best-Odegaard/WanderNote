## 1. 产品定位

### 1.1 一句话定位

> **WanderNote 是一个全方面旅游助手：用点击式对话把「模糊的出行念头」补全成「带酒店、带路线、带购票入口的完整行程」，并在出行当天真正用得上。**

### 1.2 定位的三层含义

| 层 | 含义 | 对应能力 |
|---|---|---|
| **决策层** | 帮用户**想**：不知道去哪、不知道玩什么，也能量身推荐 | 探索页 · 城市超级景点 · 吃/玩/景点三大内容 |
| **编排层** | 帮用户**定**：不用想问题，点几下就把天数、预算、酒店风格、出发地补全 | 二级提问系统 · 槽位状态机 |
| **执行层** | 帮用户**走**：买票、订酒店、导航一条链路打通 | 12306 车次 · 携程酒店深链 · 高德/百度/腾讯导航 |

### 1.3 与旧版定位的差异

| 维度 | 旧版（v1.x） | 新版（v2.0） |
|---|---|---|
| 产品形态 | AI 行程生成器 | **全方面旅游助手** |
| 冷启动 | 表单前置（6 项 + 4 题必答） | **对话即入口，点击式二级提问** |
| 用户负担 | 需要自己想清楚再填 | **用户不需要想问题，AI 问、用户点** |
| 终点 | 生成一份行程单 | 行程单 → **酒店 + 路线 + 购票入口**（可执行） |
| 内容 | 景点库/社区 | **城市超级景点（近期热点）驱动的探索** |

## 2. 目标用户与场景

### 2.1 两类核心用户（产品按此分流）

| 类型 | 特征 | 典型表达 | 产品应对 |
|---|---|---|---|
| **A 类：对行程不清晰的** | 有出行意愿，没有具体目标 | 「周末想去周边玩玩」「不知道去哪好」 | 探索驱动：城市超级景点 → **吃 / 玩 / 景点** 三类内容种草 → 一键带入对话 |
| **B 类：有清晰地点的** | 已有明确目的地或 POI | 「我要去肇庆七星岩」「想去重庆洪崖洞」 | 目标驱动：确认目标 → 问「想体验什么项目」→ **推荐顺带可以参与的项目** → 补全骨架 |

> 两类用户**收敛到同一条对话流**，区别只在首轮上下文不同（A 类带城市/主题，B 类带具体 POI 或坐标）。

### 2.2 A 类用户的三类内容模型

| 分类 | 定义 | 内容示例 | 数据字段建议 |
|---|---|---|---|
| **吃** | 当地特色小吃、必买特产 | 肇庆裹蒸粽、重庆小面、成都兔头 | `category=food`、`sub_type=snack\|specialty` |
| **玩** | 当地**特有**的可参与项目 | 漓江竹筏、三亚赶海、草原骑马、非遗手作 | `category=experience`、`is_unique_local=true` |
| **景点** | 特殊场景、独一无二 | 日出机位、溶洞、天空之镜、夜景平台 | `category=spot`、`scene_type`（日出/夜景/地质/人文） |

**内容质量标准（硬性）**：每条内容必须给出「**为什么值得专门去**」的一句话理由（`highlight_reason`），禁止罗列无差异的通用景点。

### 2.3 B 类用户的两步确认

```
确认目标 POI
   ↓
① 想体验的项目？（当地特有：竹筏 / 骑行 / 手作 / 夜游 / 温泉 …）
   ↓
② 推荐顺带可以参与的项目（基于地理邻近 + 时间窗口 + 偏好，附「顺路」理由）
```

**「顺带推荐」的生成规则**：
1. 与目标点直线距离 ≤ 3km 或同一条交通线上；
2. 游玩时长 ≤ 目标点的 50%，不喧宾夺主；
3. 开放时间与目标点时段不冲突；
4. 至多 3 个，且必须说明「顺路原因」（如「距七星岩 1.2km，落羽杉观赏期至 1 月」）。

## 3. 设计原则

| # | 原则 | 落地要求 |
|---|---|---|
| P1 | **用户不需要想问题** | AI 主动提问；每个问题都给 3-5 个可点选项；任何时候可「跳过 / 不确定」 |
| P2 | **点击优先于打字** | 目标：≥80% 的回答通过点击 chips 完成 |
| P3 | **每轮只问一件事** | 一条消息只承载一个问题，降低认知负担 |
| P4 | **随时可出结果** | 满足最小集即可生成骨架，不等问卷答完 |
| P5 | **渐进式浮出** | 能力入口（酒店、完整路线）随信息充分度**浮现**，而不是一开始就摆出来 |
| P6 | **不编造** | 无法确认的信息显式标注「待确认」；价格/时刻来自数据源而非模型生成 |
| P7 | **出行时可用** | 行程必须能离线打开、单屏阅读、一键导航 |

## 5. 核心功能设计

### 5.1 探索：城市超级景点

**目标**：承接 A 类用户，把「不知道去哪」变成「就它了」。

#### 5.1.1 城市页签

- 横向滚动页签，排序依据：**近期热点权重**（`hot_score`），而非固定热门榜。
- 热点来源（按优先级）：
  1. 运营手动配置的当期活动（节庆、赛事、花期）；
  2. 站内行为热度（近 7 日行程生成次数、点击量）；
  3. 季节因子（如 12 月 → 温泉/雪景权重提升）。
- 每个页签展示城市名 + 热点标签（如「落羽杉季」「花市」）。

#### 5.1.2 超级景点卡

| 元素 | 说明 |
|---|---|
| 大图 + 名称 | 首屏 1-2 张，视觉冲击优先 |
| 热点标签 | 「近期热点」角标，来自 `hot_score` / 运营配置 |
| **一句话理由** | `highlight_reason`，如「全国最大溶洞群，冬季恒温 20℃」 |
| 三类入口 | 吃 / 玩 / 景点 三个胶囊，点开进入对应内容分区 |
| 主 CTA | **「就这里，帮我规划」** → 进入对话，上下文携带城市 + 该景点 |

#### 5.1.3 城市详情页（吃 / 玩 / 景点）

```
┌────────────────────────────────┐
│ ‹  肇庆 · 落羽杉季        分享 │
├────────────────────────────────┤
│ [超级景点大卡：七星岩]          │
│  全国最大溶洞群 · 冬季恒温 20℃  │
│  [ 就这里，帮我规划 ]           │
├────────────────────────────────┤
│ [ 吃 ] [ 玩 ] [ 景点 ]  ← 分区  │
├────────────────────────────────┤
│ 吃 · 当地特色小吃与必买特产      │
│  · 裹蒸粽 ……  [加入行程]        │
│  · 鼎湖山茶 …… [加入行程]       │
├────────────────────────────────┤
│ 玩 · 当地特有项目                │
│  · 星湖竹筏夜游  [加入行程]      │
├────────────────────────────────┤
│ 景点 · 特殊场景                  │
│  · 七星岩落羽杉（12-1 月）       │
└────────────────────────────────┘
```

**关键交互**：任意内容卡片都有「**加入行程**」，点击后进入对话并追加为「必去项」，**不打断当前对话**。

#### 5.1.4 数据与运营

- 复用 `scenic_spot`（`ScenicSpot`）与 `home_city`（`HomeCity`），新增字段：`is_super`、`hot_score`、`highlight_reason`、`category(food|experience|spot)`、`scene_type`、`season_months`。
- 管理后台新增「超级景点运营」页：按城市配置超级景点与热点标签，支持时段生效。

### 5.2 双入口分流

| 入口 | 用户状态 | 首轮上下文 | 首句 AI 提问 |
|---|---|---|---|
| 探索页 / 城市卡片 | A 类 | `city` + `theme` | 「肇庆 12 月最值得去的是七星岩落羽杉，你想玩几天？」 |
| 首页搜索框 | A/B 类 | 自由文本 | 解析文本 → 缺什么问什么 |
| 景点详情 | B 类 | `poi` + `coords` | 「七星岩大概留 3 小时，你想体验竹筏还是溶洞讲解？」 |
| 行程导入（链接/截图） | B 类 | 解析出的地点列表 | 「我从攻略里识别出 5 个地方，要顺路排成 2 天吗？」 |

**统一约束**：无论从哪进，用户看到的都是**同一个对话界面**，只是开场问题不同。避免多套流程。

### 5.3 二级提问系统（核心机制）

这是本次重构的**心脏**。目标：**让用户不需要想问题**。

#### 5.3.1 交互形态

```
┌──────────────────────────────────────┐
│  ✦ 肇庆 12 月最值得去的是七星岩，    │
│    落羽杉正好是观赏期。你想玩几天？   │
│                                      │
│  ┌──────┐ ┌──────┐ ┌──────┐         │
│  │ 1 天 │ │ 2 天 │ │ 3 天 │  …      │  ← 点击即答（chips）
│  └──────┘ └──────┘ └──────┘         │
│  ┌──────────────┐                    │
│  │ 跳过 / 还没想好 │                   │
│  └──────────────┘                    │
├──────────────────────────────────────┤
│ [ 输入你的想法... ]              [发送]│
├──────────────────────────────────────┤
│ 需求完整度 ▓▓▓▓▓▓░░░░ 60%            │  ← 渐进反馈
│ [🏨 选酒店]  [🗺️ 生成完整路线]        │  ← 条件满足时浮现
└──────────────────────────────────────┘
```

#### 5.3.2 「二级提问」的定义

> **一级提问**：确定行程的骨架参数（去哪儿、几天）。
> **二级提问**：基于用户上一步的选择，**动态生成**的更具体问题。

**示例（动态展开）**：

```
Q1 目的地      → 用户点「肇庆」
     ↓ 派生
Q2 天数        → 用户点「2 天」
     ↓ 派生
Q3 同行人      → 用户点「亲子」
     ↓ 派生（因「亲子」而特有）
Q4 孩子年龄段  → 用户点「3-6 岁」
     ↓ 派生（因「2 天 + 亲子」而特有）
Q5 节奏        → 用户点「轻松，不想爬山」
     ↓ 派生
Q6 酒店风格    → 用户点「亲子友好 / 有泳池」
     ↓
✅ 达到阈值 → 浮出「酒店选择」+「生成完整路线」
```

**注意**：Q4（孩子年龄）只在同行人 = 亲子时出现；若用户选了「双人」，则替换为「是否想要安静 / 私汤」等。**问题不是固定清单，而是树**。

#### 5.3.3 问题树规范

每个问题节点的数据结构：

```jsonc
{
  "slot": "days",                       // 槽位 key
  "text": "你想玩几天？",                // 问题文案（≤ 20 字）
  "options": [                          // ≤ 5 个，超出改为二级页
    { "label": "1 天", "value": 1 },
    { "label": "2 天", "value": 2 },
    { "label": "3 天", "value": 3 }
  ],
  "allow_skip": true,                   // 是否可跳过
  "skip_label": "还没想好",
  "default_when_skip": 2,               // 跳过时用默认值（可被用户后续修改）
  "priority": 10,                       // 冲突时的提问顺序
  "depends_on": { "companion": ["亲子"] },  // 触发条件
  "hint": "多数人玩 2 天刚好"            // 可选：一句话建议，降低决策压力
}
```

**提问调度规则（重要）**：

| # | 规则 | 理由 |
|---|---|---|
| R1 | **每轮只问 1 个问题** | 降低压迫感，模拟真人对话 |
| R2 | 优先问 `priority` 高且**未被推断**的槽位 | 避免重复劳动 |
| R3 | 能从上下文**推断**的不问（如从坐标推断城市） | 用户不需要想 |
| R4 | 单次会话**最多 6 轮**提问，之后直接出结果 | 防止追问疲劳 |
| R5 | 任何问题都能跳过，跳过即用默认值并在行程中标为「默认」 | 不阻断 |
| R6 | 用户可随时点「**直接生成**」，立即中断提问 | 尊重用户节奏 |
| R7 | 已答槽位在后续对话中可被自然语言覆盖 | 「改成 3 天」生效 |

#### 5.3.4 必答槽位与推荐槽位

| 级别 | 槽位 | 说明 |
|---|---|---|
| **Must（最小可生成集）** | `destination`、`days` | 满足即可生成**骨架** |
| **Should（推荐集）** | `departCity`、`dateRange`、`people`、`budget`、`hotelStyle` | 用于**完整路线 + 酒店 + 购票** |
| **Nice（个性化集）** | `companion`、`pace`、`interests`、`mustVisit`、`avoid` | 提升质量，不阻断 |

> **设计要点**：`departCity`（出发地点）影响火车票与首日路线，属 Should 而非 Must——用户没定也能先出骨架。

#### 5.3.5 追问话术规范

| 要求 | 示例 |
|---|---|
| ≤ 20 字，口语化 | ✅「你想玩几天？」　❌「请选择您的出行天数区间」 |
| 带一句建议降低决策成本 | 「多数人玩 2 天刚好」 |
| 选项用**具体**表达 | ✅「轻松，不想爬山」　❌「低强度」 |
| 不重复问已知信息 | 已知「2 人」不再问人数 |

### 5.4 充分度判定与浮出工具条

#### 5.4.1 完整度计算

```
完整度 = Σ(已填槽位权重) / Σ(全部槽位权重)

权重建议：destination 25 / days 20 / departCity 10 / dateRange 10
          people 10 / budget 10 / hotelStyle 10 / companion 5
```

#### 5.4.2 浮出规则

| 条件 | 浮现内容 | 位置 |
|---|---|---|
| Must 满足（目的地 + 天数） | 「✨ 生成行程骨架」按钮常亮 | 输入框上方 |
| 完整度 ≥ 50% | 「🏨 选酒店」胶囊 | 聊天页底部工具条 |
| 完整度 ≥ 60% **且** `departCity` 已知 | 「🚂 查车票」胶囊 | 聊天页底部工具条 |
| 完整度 ≥ 60% **且** `hotelStyle` 已知 | 「🗺️ 生成完整路线」按钮（主 CTA） | 聊天页底部工具条 |
| 完整度 ≥ 80% | AI 主动提示「信息够了，我直接生成完整路线？」 | 对话消息 |

**交互要求**：
- 工具条**渐显动画**（不突兀），出现时给一次轻震动/微提示；
- 用户可**手动收起**，但下次满足条件时不再重复强提示；
- 已浮现的入口**不会因用户改答案而消失**（只会依据新状态更新），避免闪进闪出。

#### 5.4.3 状态回传

`/travel/chat` 每轮响应必须携带：

```jsonc
{
  "reply_text": "……",
  "next_question": { "slot": "budget", "text": "预算大概多少？", "options": [...] },
  "slots": { "destination": "肇庆", "days": 2, "companion": "亲子" },
  "completeness": 0.6,
  "ready": { "frame": true, "hotel": true, "transport": false, "fullRoute": true }
}
```

前端**只依据 `ready` 渲染工具条**，不在前端重复判定业务逻辑。

#### 5.6.2 导航：现实限制与方案（必读）

> ⚠️ **硬限制（已核实）**：高德地图 URI API `https://uri.amap.com/navigation` 的 `via` 参数**最多只支持添加 1 个途经点**，且途经点**仅在驾车模式下有效**。
> 来源：[高德 URI API · 路径规划文档](https://developer.amap.com/api/uri-api/guide/travel/route)
>
> **因此，「把全天所有点一次性导入高德」在官方 URI 能力下无法实现。** 必须按下面的方案设计，不能对用户承诺「一键导入全天」。

**方案 A（推荐，P0 落地）：应用内自绘 + 接续导航**

| 部分 | 实现 |
|---|---|
| 全天路线展示 | 应用内自绘（已有 `TripMap` + 腾讯地图 polyline + 地理编码能力），一次画出酒店→各点→酒店的完整路径 |
| 导航唤起 | **分段接续**：从「当前点」到「下一个点」唤起地图 App；到达后自动推进到下一段 |
| 起终点闭环 | 第一段起点固定为酒店，最后一段终点固定为酒店 |
| 交互 | 顶部显示「第 2/5 段 · 下一站：七星岩」，提供「上一段 / 下一段 / 跳过此点」 |

**方案 B（降级/补充）：路书清单页**
生成含全部坐标的分享页，用户逐点唤起地图。体验弱于方案 A，仅作为兜底。

**方案 C（不推荐，暂不做）**：接入高德/百度**导航 SDK** 自建导航。成本高、包体积大，与「轻助手」定位冲突。

#### 5.6.3 地图选择

用户点击「一键导航全天路线」→ **弹出地图选择**（用户明确要求「请选择导航的地图」）：

| 地图 | 唤起方式 | 说明 |
|---|---|---|
| 高德 | `https://uri.amap.com/navigation?from=lon,lat,酒店&to=lon,lat,景点&via=…&mode=car&policy=1&src=wandernote&callnative=1` | `callnative=1` 在微信/QQ 内置浏览器无法调起，需兜底 Web |
| 百度 | `baidumap://map/direction?origin=latlng:…|name:…&destination=…&mode=driving` | 无 App 时降级 H5 |
| 腾讯 | `https://apis.map.qq.com/uri/v1/routeplan?...` | 项目已用腾讯位置服务，Key 现成 |

**实现要求**：
- 统一封装在 `frontend/src/utils/deeplink.ts`；
- 必须做**调起失败探测**（`setTimeout` + `visibilitychange`），失败则提示「未检测到该地图 App」并给出 H5 链接；
- 记住用户上次选择，默认沿用（但仍可切换）。

## 6. 槽位状态机与数据结构

### 6.1 槽位定义（前端 + Agent 共享）

```ts
type SlotKey =
  | 'destination' | 'days' | 'dateRange' | 'departCity'
  | 'people' | 'companion' | 'budget' | 'hotelStyle' | 'hotelArea'
  | 'pace' | 'interests' | 'mustVisit' | 'avoid'

interface SlotState {
  key: SlotKey
  value: string | number | string[] | null
  source: 'user' | 'inferred' | 'default' | 'imported'   // 来源，用于 UI 标注
  confidence: number                                      // 0-1，推断来源用
  asked: boolean                                          // 是否已问过
  skippable: boolean
}
```

### 6.2 状态迁移

```
INIT
  │  用户首轮输入 / 从探索页带入
  ▼
COLLECTING ──(每轮: 回答 or 跳过 or 推断)──► 更新 slots + completeness
  │                                              │
  │  Must 满足                                    │ completeness ≥ 60%
  ├──────────────► FRAME_READY（骨架按钮可用）    ├────────► TOOLBAR_READY（浮出工具条）
  │                                              │
  │  用户点「直接生成」                            │ 用户点「生成完整路线」
  └──────────────► GENERATING ◄──────────────────┘
                     │
                     ▼
                  DONE（可编辑 / 可分享 / 可出行）
```

**关键规则**：`COLLECTING` 状态**不阻塞**生成。任何时刻用户都能生成。

### 6.3 问题树调度伪代码

```ts
function nextQuestion(slots: SlotState[], askedCount: number): Question | null {
  if (askedCount >= 6) return null                    // R4：最多 6 轮
  const candidates = QUESTION_TREE
    .filter(q => !slots[q.slot]?.value)               // R2：未填
    .filter(q => !slots[q.slot]?.asked)               // 不重复问
    .filter(q => matchesDependsOn(q, slots))          // 依赖满足
    .filter(q => !canInfer(q.slot, slots))            // R3：可推断则不问
    .sort((a, b) => b.priority - a.priority)
  return candidates[0] ?? null                        // R1：只返回一个
}
```

## 11. 验收标准

| # | 指标 | 目标值 | 测量方式 |
|---|---|---|---|
| 1 | 冷启动到「第一版骨架可见」 | ≤ 30 秒 | 埋点 `plan_start` → `plan_generated` |
| 2 | 冷启动点击次数 | ≤ 3 次 | 埋点计数 |
| 3 | 点击式回答占比 | ≥ 80% | `slot_answer` 的 `source=chip` / 总数 |
| 4 | 平均提问轮次 | ≤ 5 轮 | `slot_asked` 计数 |
| 5 | 跳过率（可接受区间） | 15%-40% | 过低=问题无价值，过高=问题难答 |
| 6 | 工具条浮现准确性 | 100% 符合 5.4.2 规则 | 端到端用例 |
| 7 | 完整路线闭环 | 每条路线起点与终点均为酒店 | 数据校验 |
| 8 | 导航唤起成功率 | ≥ 95%（主流机型） | 端到端 + 失败埋点 |
| 9 | 酒店跳转携带参数正确 | 城市 + 日期 + 关键词齐全 | 链接断言测试 |
| 10 | 探索 → 对话转化率 | ≥ 25% | 埋点 |
| 11 | 出行当日行程打开率 | ≥ 20% | 埋点 `trip_opened_ontrip` |

**埋点清单**：`plan_start` / `slot_asked` / `slot_answer` / `slot_skip` / `toolbar_shown` / `toolbar_tapped` / `hotel_selected` / `hotel_ctrip_click` / `train_query` / `train_12306_click` / `nav_invoke` / `nav_fail` / `plan_generated` / `trip_opened_ontrip`

## 12. 风险与合规

| # | 风险 | 等级 | 应对 |
|---|---|---|---|
| R1 | **12306 数据来源无官方公开 API** | 🔴 高 | 优先做「跳转 12306 查询/购买」；如需展示班次，必须走有授权的数据服务商并留存授权凭证。**绝不代购、绝不存用户账号** |
| R2 | 携程深链格式变更 | 🟡 中 | 深链构造收敛到单一函数 `buildCtripHotelUrl()`；建立监控，跳转失败率 > 5% 告警 |
| R3 | 高德 URI 途经点限制（已核实：仅 1 个、仅驾车） | 🟡 中 | 采用「应用内自绘 + 分段接续导航」，**不向用户承诺一键导入全天** |
| R4 | 微信内置浏览器无法调起地图 App | 🟡 中 | `callnative` 失效时降级为 H5 导航页；小程序内使用 `wx.openLocation` |
| R5 | 酒店「参考价」被误认为实时价 | 🟡 中 | 全站统一文案「参考价，以携程为准」；禁止出现「可订」「有房」字样 |
| R6 | 知识库过薄导致幻觉（现仅 10 条景点 seed） | 🔴 高 | 重构同期扩充 KB；未收录城市在 UI 显式标注「部分信息待确认」 |
| R7 | 截图/链接导入的版权与合规 | 🟢 低 | 仅解析用户主动提供的内容，用于生成私人行程，不做公开传播 |
| R8 | 位置权限被拒 | 🟢 低 | 手动选择出发地作为兜底，不阻断流程 |

## 附录 A：与市场调研结论的对应关系

| 调研结论（出处见市场调研报告） | 本文档对应设计 |
|---|---|
| AI 规划头号缺陷是「缺乏灵活性 54.7%」 | 5.3 二级提问可随时改答；P0 局部重排（阶段三） |
| 42% 用户总是核查 AI 内容 | P6 不编造原则；价格/时刻来自数据源；「待确认」标注 |
| 决策临期化（58.3% 当天预订） | 首屏 ≤ 30 秒出骨架；问题树规则引擎不走 LLM（100ms 级） |
| 协作是第一压力源（协调时间 75.8%） | 阶段三协作与投票 |
| 小红书「超 80% 先做攻略」但收藏变不成行程 | 5.2 行程导入入口（链接/截图解析）；探索 → 对话转化 |
| 内容平台占据种草，OTA 占据交易 | 本产品占「**编排层**」；交易全部深链跳转，不自建库存 |
| 马蜂窝 AI 路书「主动提问 + 选择题」是行业最优交互 | 5.3 二级提问系统的直接对标与超越（问题树 > 单轮反问） |
| Google Canvas 把「可编辑」当卖点 = 行业普遍缺失 | 5.3.3 R7 已答槽位可自然语言覆盖 |
| TripTailor：SOTA LLM 行程不到 10% 达人类水平 | 不假设一次生成即完美；「生成 → 点击微调 → 再生成」为主干 |

## 附录 B：术语表

| 术语 | 含义 |
|---|---|
| **槽位（Slot）** | 行程的一个参数项（如天数、预算） |
| **二级提问** | 基于用户上一轮选择**动态派生**的更具体问题 |
| **完整度（Completeness）** | 已填槽位权重和 / 总权重，用于驱动工具条浮现 |
| **浮出工具条** | 信息充分后从聊天页底部渐显的「酒店 / 车票 / 完整路线」入口 |
| **接续导航** | 分段唤起外部地图，走完一段自动推进到下一段 |
| **闭环路线** | 以酒店为起点与终点的当日路线 |
| **超级景点** | 某城市当期最值得去的 1-2 个景点，带热点标签与一句话理由 |
