## 二、P0 级 Bug（核心功能不可用）

### Bug 1：「生成行程计划」必然超时失败（最严重）

- **现象**: 点击生成按钮后约 **29.2s** 弹「生成最终行程失败」，请求被 abort（`net::ERR_ABORTED`）。实测重复 3 次稳定复现。
- **根因链**:
  1. 前端 `src/utils/constant.ts` `REQUEST_TIMEOUT = 30000`（30 秒）；
  2. 后端 `POST /travel/generatePlan` 实测耗时 **124.7s**（调 Python Agent `/api/plan`）；
  3. Python Agent `agent/travel_agent.py` 的 `plan_stage` 用 `deepseek-v4-pro` + `with_structured_output(TripPlan)` 同步生成结构化 JSON，且每个景点带 3 张 `photos_json` 图片 URL，输出 token 巨大、含重试，导致极慢；
  4. 后端 `RestTemplate`（`WebMvcConfiguration.java` 第 166 行）未配置任何超时，只能无限等待。
- **影响**: AI 行程生成的入口功能 100% 失败，用户永远到不了行程详情页。
- **建议**:
  - 前端：`REQUEST_TIMEOUT` 提到 180s+，或后端改异步任务 + 轮询；
  - Agent：`photos_json` 每景点减到 1 张、关闭/减少 `with_structured_output` 重试、`plan_stage` 改 async；
  - 后端：给 RestTemplate 配 `connectTimeout/readTimeout`（如 150s）。

### Bug 2：`POST /travel/aiPlan` 超慢且返回空数据

- **现象**: 耗时 **83.5s**，返回实体字段几乎全空：`travelPreference=null`、`planTitle=null`、`agentFullStrategy=null`、`firstDayDate=null` 等。
- **根因**: `TravelScheduleServiceImpl.createPlanByAi`（第 50-53 行）里把 AI 返回的行程数据映射代码**全部注释掉了**，AI 生成的 `plan_data` 被直接丢弃，只入库回传一个空壳实体。前端 `generate.vue` 若走此链路拿不到任何行程内容；且 83.5s 同样远超前端 30s 超时。
- **建议**: 实现 plan_data → TravelSchedule 的映射入库；若该接口已废弃，前端应移除入口（generate.vue 目前是重定向到 chat 的占位页）。

### Bug 3：行程保存/列表/更新/删除接口后端缺失

- **现象**: 「我的行程」页空白，控制台报 `TypeError: Cannot read properties of null (reading 'length')`。
- **根因**: 前端 `src/api/trip.ts` 调用 7 个接口，后端 `TripPlanController` 只实现了 2 个：
  | 前端调用 | 后端 | 实测结果 |
  |---|---|---|
  | `POST /trip/generate` | ❌ 无 | 404 |
  | `POST /trip/save` | ❌ 无 | 404（保存行程不可用）|
  | `GET /trip/list` | ❌ 无（被 `GET /trip/{id}` 拦截）| `NumberFormatException: "list"` |
  | `GET /trip/{id}` | ✅ | 正常 |
  | `PUT /trip/{id}` | ❌ 无 | 405 |
  | `DELETE /trip/{id}` | ❌ 无 | 405 |
  | `POST /trip/import/link` | ✅ | 正常 |
- **影响**: 生成的行程无法保存、我的行程无法查看——第二个核心闭环断裂。
- **建议**: 补全 `TripPlanController` 的 list/save/update/delete/generate 接口（Service 层 `TripPlanServiceImpl` 是否已有实现需检查）；另外 `pages/trip/index.vue` 的 `loadTrips()` 没有 try/catch，接口失败时 `loading` 卡死、`trips` 为 null 触发后续报错，需兜底。

## 三、P1 级 Bug（功能异常）

### Bug 4：登录回跳 redirect 双重编码 + 参数根本没被使用

- **现象**: 未登录访问受保护页，跳登录时 URL 为 `redirect=%252Fpages%252Fhome%252Findex`（`%2F` 被二次编码成 `%252F`）。且 `src/utils/auth.ts:30` 用 `encodeURIComponent` 编码后，uni-app H5 框架还会再编码一次。
- **更严重**: `useLogin.ts` 的 `handleLogin` 成功回调**完全不读取 redirect 参数**，只 `navigateBack`/`switchTab` 回首页。也就是说：用户从「行程」页被踢去登录，登录成功后不会回到「行程」页。
- **建议**: 登录成功时解析 `redirect` 参数（解码一次即可）并 `uni.redirectTo` 回去；或直接用 `uni.navigateBack` 依赖页面栈（当前行为）。

### Bug 5：用户资料类接口缺失

- `GET /user/info`、`PUT /user/info`、`POST /user/sms` 后端全部 404（`UserController` 只有 register/login）。「我的」页、资料编辑页、短信登录都会挂。
- **建议**: 实现 `/user/info` 查询/更新（JWT 取 userId），或前端隐藏这些入口。

### Bug 6：景点/活动接口全部 404

- `/scenic/list`、`/scenic/search`、`/scenic/hot`、`/activity/list`、`/activity/hot` 全部 404——后端**没有任何 scenic/activity 的 Controller**。景点列表、搜索、活动页全挂。
- **建议**: 补 Controller + Service，或前端先用 mock/静态数据兜底再逐步接入。

### Bug 7：`GET /journal/hot` 被 `/journal/{id}` 路由拦截

- **现象**: 返回 200 但业务码失败：`Failed to convert value of type 'java.lang.String' to required type 'java.lang.Long'`（"hot" 被当 id 解析）。
- **根因**: `TravelJournalController` 有 `/list` 和 `/{id}`，但前端调的是 `/journal/hot`，无此映射 → 落入 `/{id}`。
- **建议**: 增加 `@GetMapping("/hot")` 映射。

### Bug 8：AI 聊天历史每轮重复入库（数据膨胀）

- **根因**: `ChatServiceImpl.chat()`（第 52-63 行）每轮把**完整历史**（含此前所有轮次）重新 `insert` 一遍。第 n 轮会插入 2n 条记录，长对话后 chat_history 表数据量平方级膨胀，且多轮请求体越来越大，还会进一步拖慢 `/travel/chat`。
- **建议**: 只插入本轮新增的 user + assistant 两条（或按 session 去重）。

### Bug 9：`GET /ai/history` 404

- 前端 `getAiHistory`（`trip.ts`）调用 `GET /ai/history`，后端无此接口（当前 chat.vue 未实际调用，但接口文档已声明存在）。
- **建议**: 实现或删除。

## 四、P2 级问题

1. **Agent 阻塞事件循环**: `main.py` 的 async 端点内同步调用 `.invoke()`（`plan_stage`），并发请求会互相阻塞。建议用 `asyncio.to_thread` / 线程池。
2. **`/travel/chat` 首次对话 ~20s**：勉强在 30s 超时线内，但多轮历史变大后可能超时（与 Bug 8 相互放大）。
3. **`pages/ai/generate.vue` 是空壳**: 仅 `uni.redirectTo('/pages/ai/chat')`，路由指向了 chat 页，若无历史包袱建议从 pages.json 移除，避免路由歧义。
