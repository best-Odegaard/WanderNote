## 四、根因分析

### 4.1 占位串来自哪里

`坐标数据待核实` 这个串**在 geek012 后端代码里搜不到，在本地 `travel_self_agent/` 副本里也搜不到**，
它来自**线上真正在跑的那个智能体**（`/www/DXY/educate/travel_self_agent`，与本地仓库副本不是同一份代码）。
智能体在解析不到景点门牌坐标时，会往 `location` 和 `description` 里写入这个占位标记。

它的 `description` 模板形如：`📍{location} | 🕒{openTime} | 💰{ticket}`。

### 4.2 当前实现（提交里的做法）

```java
// AdminFeaturedTripServiceImpl
private void stripPlaceholder(JSONObject spot, String key) {
    String val = spot.getString(key);
    if (val != null) {
        spot.put(key, val.replace("（坐标数据待核实）", "").trim());
    }
}
```

对 `location` 和 `description` 各做一次**无脑字符串替换**。它只覆盖了"字段里还混着别的文字"这一种情况。

#### 缺陷 1：`location` 清完变空字符串（**这条是有实际功能收益的修正**）

那 15 处 `location` 只有占位串的，替换后得到 `""`。为什么应该改成移除字段：

```javascript
// src/utils/geo.ts:137
export function geocode(address, city, name) {
  let query = address || name || ''      // ← 空字符串是 falsy，会回退用景点名
  if (!query) return Promise.resolve(null)
  ...
}

// src/pages/trip/detail.vue:570
const ll = await geocode(s.location || s.title, city, s.title)
```

| `location` 的值 | 发给地图接口的查询词 | 结果 |
|---|---|---|
| `（坐标数据待核实）`（现状） | `肇庆（坐标数据待核实）` | ❌ 必然查不到，且**不会**回退用景点名 → 景点不上图 |
| `""`（当前实现的产物） | `肇庆牌坊广场`（靠 `\|\|` 兜底） | ✅ 有机会定位成功 |
| 字段被移除 / `null`（建议） | `肇庆牌坊广场` | ✅ 同上，且语义明确 |

也就是说：**清洗本身能顺带修好这 15 个景点的地图定位**（从"必然失败"变成"标题兜底"）。
但把字段留成空串是"靠调用方写 `||` 才不出事"，属于脆弱写法 —— 建议直接移除该字段，语义更明确。

#### 缺陷 2：`description` 留下悬空的 `📍`

`description` 是分段的整串，只做全局替换会把地址段的图标和分隔符留下：

```
清洗前：📍（坐标数据待核实） | 🕒现场咨询 | 💰现场咨询
清洗后：📍 | 🕒现场咨询 | 💰现场咨询      ← 地址段空了，但「📍 | 」还在
```

**严重度要客观说**：因为 App 端**不渲染 `description`**，用户不会直接看到它；
影响面是管理端 JSON 的可读性、以及将来若有功能消费该字段时会读到脏数据。属**数据整洁问题**，不是用户可见缺陷。

#### 缺陷 3：抓取的是"新产出"，存量一行没动

`cleanTripJson` 只在 `parseLink` 里被调用，也就是**只有后台新解析生成的草稿**会被洗。
已经入库的 22 行 / 176 处完全不受影响 —— **用户抱怨的那个"满屏"依然在**。

## 六、解决方案

### 方案 A（推荐）：把「字符串替换」升级为「按字段语义清洗」

```java
/** 智能体在无法核实坐标时会写入这个占位标记。它只对内部排查有意义，不该出现在地址/描述里 */
private static final String COORD_PLACEHOLDER = "（坐标数据待核实）";

/** description 是「📍地址 | 🕒开放时间 | 💰门票」拼好的整串，这段前缀就是地址段 */
private static final String DESC_ADDR_PREFIX = "📍";

/**
 * 清洗单个景点的地址与描述。
 * 比原来的 replace 多做了两件事：
 *   1. location 清完为空时**移除字段**，而不是留空字符串 —— 空值和"没有地址"语义一致，
 *      前端 geocode 也能顺着 s.location || s.title 回退用景点名（空串同样能兜底，但留着字段早晚踩坑）。
 *   2. description 是分段的整串，地址段清空后要把那一段连同分隔符一起丢掉，
 *      否则会留下悬空的「📍 | 」。
 */
private void cleanSpot(JSONObject spot) {
    String location = spot.getString("location");
    if (location != null) {
        String cleaned = location.replace(COORD_PLACEHOLDER, "").trim();
        if (cleaned.isEmpty()) {
            spot.remove("location");
        } else {
            spot.put("location", cleaned);
        }
    }

    String description = spot.getString("description");
    if (description != null) {
        List<String> kept = new ArrayList<>();
        for (String segment : description.split("\\|")) {
            String s = segment.replace(COORD_PLACEHOLDER, "").trim();
            // 地址段清空后只剩一个 📍，整段丢掉
            if (s.isEmpty() || DESC_ADDR_PREFIX.equals(s)) {
                continue;
            }
            kept.add(s);
        }
        if (kept.isEmpty()) {
            spot.remove("description");
        } else {
            spot.put("description", String.join(" | ", kept));
        }
    }
}
```

`cleanTripJson` 相应改为（同时按元素类型做了保护，见第九节）：

```java
private String cleanTripJson(String tripJson) {
    try {
        JSONObject trip = JSON.parseObject(tripJson);
        JSONArray dayPlans = trip.getJSONArray("dayPlans");
        if (dayPlans != null) {
            for (int i = 0; i < dayPlans.size(); i++) {
                JSONObject day = dayPlans.getJSONObject(i);
                if (day == null) continue;
                JSONArray schedules = day.getJSONArray("schedules");
                if (schedules == null) continue;
                for (int j = 0; j < schedules.size(); j++) {
                    Object item = schedules.get(j);
                    if (item instanceof JSONObject) {
                        cleanSpot((JSONObject) item);
                    }
                }
            }
        }
        return trip.toJSONString();
    } catch (Exception e) {
        log.warn("行程内容清洗失败，按原文返回：{}", e.getMessage());
        return tripJson;
    }
}
```

**效果对照：**

| 输入 | 当前实现 | 方案 A |
|---|---|---|
| `location` = `端州区端州五路（坐标数据待核实）` | `端州区端州五路` ✅ | 同 ✅ |
| `location` = `（坐标数据待核实）` | `""` ⚠️ | 字段移除 ✅ |
| `description` = `📍端州区端州五路（坐标数据待核实） \| 🕒24小时营业` | `📍端州区端州五路 \| 🕒24小时营业` ✅ | 同 ✅ |
| `description` = `📍（坐标数据待核实） \| 🕒现场咨询` | `📍 \| 🕒现场咨询` ⚠️ | `🕒现场咨询` ✅ |
| 无占位串的字段 | 不变 ✅ | 不变 ✅ |

> 用 `spot.remove(k)` 而不是 `put(k, null)`：fastjson 默认序列化会省略 null 值，两者结果一样，
> 但 `remove` 不依赖序列化配置，意图也更清楚。

### 方案 B：存量数据回填（**这是唯一能让用户看到"满屏"消失的动作**）


**B-2 快速版（SQL，有副作用，不建议单独使用）**

两个字段都是 `text` 列，`REPLACE()` 可直接跑：

```sql
UPDATE featured_trip SET trip_json = REPLACE(trip_json, '（坐标数据待核实）', '') WHERE trip_json LIKE '%坐标数据待核实%';
UPDATE trip_plan     SET day_plans = REPLACE(day_plans, '（坐标数据待核实）', '') WHERE day_plans LIKE '%坐标数据待核实%';
```

仅适合"先止血、后续再精修"的场景。

## 九、附：顺带发现的代码问题

1. **无用导入**：`import springfox.documentation.spring.web.json.Json;` —— 全文件只有 import 行，
   无任何使用（已按用户要求在我们这边同步时删除）。
2. **被注释掉的旧代码**：`//draft.setTripJson(JSON.toJSONString(trip));` 建议一并删掉。
3. **方法命名与行为不符**：`stripPlaceholder` 做的是"删占位串"，`strip` 容易被误读成"去空白"，
   建议按语义改名（如 `removeCoordPlaceholder`）。
4. **异常兜底过粗**：整段 `try/catch` 一旦命中就"整份不清洗"，且只打一行 warn，属于**静默失效**。
   建议按元素类型判断（见方案 A 的 `instanceof JSONObject` 保护），
   别让一条脏数据或格式变化导致整份放弃清洗。
