# AI 行程规划 — 长对话上下文持久化改造方案

> 目标：让"智能体生成计划"支持长对话。每次对话入库，后续提交时把上一轮会话上下文一并带给智能体，使其具备多轮记忆能力。

## 一、现状分析

| 项 | 现状 |
|----|------|
| 数据库 `geek012` | 仅有 `sys_user / trip_plan / travel_journal* / home_* / scenic_spot / activity_info`，**无任何会话/消息存储表** |
| 后端 `AIController /ai/generate-plan` | 每次生成 `session_id = session_<时间戳>`，`user_input=""`、`chat_history=[]`，会话不持久、不复用 |
| 后端 `AgentHttpUtil.buildPythonAgentRequest` | 硬编码空历史，不回传上下文 |
| Python `main.py /api/plan` | **已支持** `chat_history: list[ChatMessage]`，`TravelAgent.build_plan_messages` 会把历史拼到 `SystemMessage` 与新 `HumanMessage` 之间 |
| 前端 `pages/ai/chat.vue` | 进入页面即调用一次 `callAiAgent`，输入框 `sendMessage` 只回复本地话术，**不回传后端** |
| MySQL 连接 | `application-dev.yml` 中 `password: '200753'` 已失效，实际可用密码为 `***（已脱敏，见本地 application-dev.yml）***` |

结论：能力缺口主要在 **①会话存储表缺失 ②后端不存历史、不回传 ③前端不提交历史**。Python 侧已就绪，无需改动。

## 三、关键设计

### 3.1 表结构（DDL 概要）

```sql
ai_chat_session:
  id, session_id(unique), user_id, title,
  base_info_json,          -- 行程表单快照(departure/destination/days/...)
  create_time, update_time, is_deleted

ai_chat_message:
  id, session_id, role('user'|'assistant'), content,
  is_plan(tinyint),         -- 1=该轮为 plan 生成结果
  plan_data_json,           -- plan 轮时存完整 PlanResponseDTO JSON
  create_time, update_time, is_deleted
  index(session_id, create_time)
```

### 3.2 多轮调用流程

```
前端 chat.vue
  └─ callAiAgent({session_id, user_input, base_info...})
       └─ POST /ai/generate-plan  (AIController)
            ├─ AiChatService.getOrCreateSession(session_id, base_info)
            ├─ 历史 = AiChatService.listHistory(session_id)  ← 上一轮及之前
            ├─ AgentHttpUtil.callAgent(base_info, user_input, 历史, session_id)
            │     └─ POST http://localhost:8002/api/plan  (chat_history 非空)
            ├─ AiChatService.appendMessage(user, user_input)
            ├─ AiChatService.appendMessage(assistant, plan结果, is_plan=1)
            └─ return {session_id, plan_data, chat_history}
```

下一轮提交时，上一轮的 user 输入 + assistant plan 摘要均在 `chat_history` 中，智能体据此优化行程。

### 3.3 兼容性
- `session_id` 为空时后端自动创建并返回，前端旧调用（不传 session_id）仍可用，只是无记忆。
- `user_input` 为空时按首轮处理，默认 `"生成最终行程"`（与 Python 现状一致）。
- Python 侧无需改动。

### 3.4 多轮生成方式
- 采用**覆盖式重生成**：每轮综合全部历史 + 本轮 `user_input` 重新输出一份完整 plan，最后一份即最终计划。简单稳定，与当前实现一致。
- 历史里 assistant 摘要**带上完整 day_list 每日景点序列**（`buildAssistantSummary`），让大模型多轮理解更精准，能精确沿用/修改上一次行程；完整结构仍存 `plan_data_json`。
- **"生成行程计划"按钮**：点击 `goItinerary` 时会**再调一次** `/ai/generate-plan`，带 `user_input="请综合以上所有讨论内容，生成最终的完整旅游行程计划"` + 当前 `session_id`，后端把全部对话上下文喂给智能体，返回的最终 plan 映射为 TripPlan 跳转详情页。即"最终计划"由整段聊天上下文综合生成，而非直接取最后那一份。

## 四、联调测试结果（2026-07-30）

### 4.1 测试环境
- 后端：`java -jar gkv-server-1.0-SNAPSHOT.jar`（端口 8080）
- Python Agent：`python main.py`（端口 8002，deepseek-v4-pro）
- MySQL `geek012`、Redis

### 4.2 第一轮（首次，无 session_id）
```
POST /ai/generate-plan
{departure_city:"广州",destination_city:"肇庆",days:2,...}
→ code=1, sessionId=sess_ca85...(后端创建), planData.title="肇庆2日自然美食休闲之旅", chatHistory.len=2
```

### 4.3 第二轮（带 session_id + user_input 追问）
```
POST /ai/generate-plan
{session_id:"sess_ca85...", user_input:"请把第二天换成鼎湖山，并增加一个特色美食点", ...}
→ code=1, sessionId 同上(复用), chatHistory.len=4
  user | isPlan=0 | 生成最终行程
  assistant | isPlan=1 | 已生成行程计划《肇庆2日自然美食休闲之旅》...
  user | isPlan=0 | 请把第二天换成鼎湖山...
  assistant | isPlan=1 | 已生成行程计划《...》...
```
第二轮 `user_input` 已成功转发给智能体（多轮记忆生效）。

### 4.4 历史查询接口
```
GET /ai/history?sessionId=sess_ca85...
→ code=1, count=4（user×2 + assistant-plan×2）
```

### 4.5 数据库落库验证
```
ai_chat_session: 1 行
ai_chat_message: 4 行（user/is_plan=0 ×2，assistant/is_plan=1 ×2）
```
