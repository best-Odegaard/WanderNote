#### 1.1 AI 用户画像功能的建表（2026-09-14 新增）

按顺序执行 `部署表结构/` 下这两个版本化脚本：

| 脚本 | 作用 | 开发库现状 |
|---|---|---|
| `V2.1__create_user_profile.sql` | 建画像主表 `user_profile`（一个用户一行） | **表已存在，脚本是 `create table if not exists`，执行等于空操作，不用管** |
| `V2.2__alter_chat_history_add_user_id.sql` | `chat_history` 加 `user_id` 列 + 索引 | **列和索引都已存在，重复执行会报 `Duplicate column name 'user_id'`，属预期，跳过即可** |

两个脚本头部都写了自查 SQL，执行完可以顺手核对一下。

> **列名以库为准，不要按文档改名。** `user_profile` 在开发库里已经建过，
> 列名是 `pref_tags / constraints / chat_round_count / last_source / use_preference / mark`。
> Java 侧按这套列名映射（见 `com.gkv.entity.UserProfile` 的 `@TableField`）。
> 如果有人按"更好看的名字"去建表或改列名，`create table if not exists` 会静默跳过，
> 代码里的列名一个都对不上 → 运行时报 `Unknown column`，
> 而画像链路整条包在 try/catch 里，表现是"功能看起来做好了但一直不生效"，非常难查。

#### 1.2 执行前必须确认的存量环境差异

本次核对开发库时发现快照 SQL 与实际库有几处不一致，**与本功能无关但会挡主链路**，
上线前请确认生产库已执行过对应变更：

- **`trip_plan` 缺 `start_date` / `end_date`**：`V1.9__alter_trip_plan_add_dates.sql` 若没执行，
  `GET /trip/list`、`GET /trip/{id}` 会直接 **500**（`Unknown column 'start_date' in 'field list'`），
  登录用户一打开首页就报错。**本次已在开发库补执行。**
- **`featured_trip` 表不存在**：`V2.0__create_featured_trip.sql` 若没执行，
  `GET /featured/list` 报 `Table 'xxx.featured_trip' doesn't exist`（首页轮播 500）。**本次已在开发库补执行。**
- `chat_history` 实际是 `role varchar(20)` / `content longtext`，快照 `chat_history.sql` 写的是 `varchar(16)` / `text`。
- `trip_plan` 实际有 `chat_session_id` 列（实体 `TripPlan.chatSessionId` 在用），
  但快照 `trip_plan_geek012.sql` 没声明这一列。
- 应用的用户表是 **`sys_user`**（`User` 实体 `@TableName("sys_user")`），不是 `user.sql` 里的 `user`。
- 库里还有 `ai_chat_session` / `ai_chat_message` 两张**没有代码在用的遗留表**：
  真正生效的对话表是 `chat_history`（走 `ChatHistoryMapper`）。本次没有使用那两张遗留表。

> 核对方法：把 18 个实体的 `@TableName` 与 `information_schema.tables` 做 diff，
> 现在缺 0 张。建议每次部署前都跑一遍这个 diff，比逐个报错去猜快得多。

#### 2.1 画像摘要模型（2026-09-14 新增，可以不配）

`application.yml` 里有三个新配置项，走 OpenAI 兼容的 `/chat/completions`，
与对话/规划用的模型**完全分开**（对话/规划的模型在 Python agent 里）：

```yaml
profile:
  summary:
    url: ${PROFILE_SUMMARY_URL:}        # 要填到 /chat/completions 为止，不是 base_url
    api-key: ${PROFILE_SUMMARY_API_KEY:}
    model: ${PROFILE_SUMMARY_MODEL:}
```

**三项任一为空 → 摘要重写直接跳过并打一行 warn，其余功能完全不受影响**
（对话照常、生成行程照常、标签权重照常累加，只是没有 AI 文字摘要）。
所以这个功能可以先不配就能上线，之后再补。

> 生产建议用环境变量注入，别把 key 提交进仓库。
> 校验方式：`grep "ProfileSummary\|ProfileRewrite" server.log`，
> 未配置时会看到「摘要模型未配置（profile.summary.url/api-key/model 存在空值），跳过摘要重写」。

### 4. Agent 服务地址（重要）
新接口会调用 Python AI Agent（`/travel/chat` → `/api/chat`，`/travel/generatePlan` → `/api/plan`）。
配置在 `application.yml`：
```yaml
agent:
  chat-url: http://<your-server-ip>:8002/api/chat
  plan-url: http://<your-server-ip>:8002/api/plan
```
**如果 agent 服务与后端部署在同一台服务器，建议改为 `http://127.0.0.1:8002/...`**，避免公网回环被防火墙拦截（本次联调中公网 IP 8002 端口从本机不可达）。

#### 4.1 请求体的必填字段（改 agent 后必检）

Agent 的 `BaseInfo` 把 **`start_day` / `end_date` 也定义成了必填**（会校验「日期从出发日连续递增，共 days 天」），
fastjson 默认丢弃 `null` 字段，所以这两个字段一旦没赋值，agent 会直接返回 **422 Unprocessable Entity**，
表现为「生成行程失败」，且日志里看不到 LLM 调用记录。

- 后端已统一用 `com.gkv.utils.TripDateUtil` 推算：没给具体出发日期时按「今天出发 + days 天」。
- 涉及两条链路：`TripPlanServiceImpl.generatePlanViaAgent`（链接导入 / 精选行程解析）与
  `TravelScheduleServiceImpl.createPlanByAi`（App 内 AI 生成行程）。
- 游记正文优先放 `base_info.context_note`（agent 专门的外部上下文入口，会作为首轮提示词）；
  放在 `chat_history` 里也能生效，但 `context_note` 是它的设计位置。

**排查口诀**：agent 日志里 `/api/plan` 返回 `422` = 请求体缺字段；返回 `500` 且堆栈里有
`Access denied, please make sure your account is in good standing` = 大模型账号（阿里云百炼 DashScope）
欠费/停用，Key 在 agent 的 `travel_self_agent/com.py`（`api_key` / `base_url1`），属于账号侧问题，改代码没用。

> **更正（2026-09-14，含线上复核）**：上面说「`context_note` 是 agent 专门的外部上下文入口」这条，
> **本地仓库那份 agent 副本上不成立，但线上是成立的**——两边的 agent 不是同一份代码（见下）。
> - **本地仓库副本** `travel_self_agent/`：`main.py` 的 `BaseInfo` 没声明 `context_note`，
>   pydantic 默认 `extra='ignore'` + 序列化走 `model_dump()`，所以传了会被静默丢弃。
> - **线上 `/www/DXY/educate/travel_self_agent`（真正在跑的）**：`BaseInfo` **已声明 `context_note`**
>   （`Optional[str]`），所以线上是生效的。
>
> ⚠️ 请以线上为准：**本地仓库这份 agent 副本和线上不是同一个代码库**，不要用本地文件覆盖线上。
> 详见 `画像功能交付说明.md` 第十一节。

#### 4.2 `/api/plan` 已经不分 mode 了（别再走两段式）

2026-09 之后服务端那份智能体的 `/api/plan` **没有 `mode` 参数**了，FastAPI 会静默忽略未知查询参数。
所以历史上的「`?mode=frame` 出骨架 + `?mode=detail` 补明细」两段式调用，会让**同一条规划管线白跑两遍**：
耗时翻倍、必然撞上读取超时，而且第一段的返回值会被当成 frame 丢掉。

- 后端现在统一走 `AgentHttpUtil.callPlan(...)`（一次调用成型），与 App 内 AI 生成链路一致。
- 游记/攻略正文放 `chat_history`（新管线**以它为唯一参考**来提取需求摘要、行程骨架、行程原文），
  `base_info.context_note` 同时带上作为备用。
- 超时配置：`RestTemplate` 单次 900s（`WebMvcConfiguration`）、管理端 axios 与 nginx 反代 1500s。

#### 4.3 Agent 是单进程同步服务

Agent 用 uvicorn 单 worker 跑，接口是同步阻塞的：**一个请求处理期间，其它请求全部排队**，
`/docs` 也会探不通。实测一个多日行程要 2~7 分钟（逐景点核门票更慢）。
如果 agent 卡在某个外部调用上（例如上游 LLM 连接无超时），它会一直挂着不退出——
此时 `pkill`（SIGTERM）无效，因为 uvicorn 的优雅退出钩子要靠事件循环，而事件循环正被阻塞，
必须 `pkill -9`（SIGKILL）后重启：

```bash
cd /www/DXY/educate && source venv/bin/activate
nohup python3 -m travel_self_agent.main >> app.log 2>&1 &
```

另外这个 agent 目前是 **geek012 与 DXY 共用同一个进程**（运行目录是 `/www/DXY/educate`），
两边会互相排队；端口 8002 还直接暴露在公网（日志里能看到 `GET /v1/models` 之类的扫描请求），
建议在防火墙只放行内网/本机访问。

### 5. 数据库表（chat_history 表结构）
```sql
create table chat_history (
    id          bigint auto_increment primary key,
    session_id  varchar(64)  not null comment '会话ID',
    role        varchar(16)  not null comment '角色：user/assistant',
    content     text         not null comment '消息内容',
    create_time datetime default CURRENT_TIMESTAMP null comment '创建时间'
) comment '聊天历史记录表';
create index idx_session_id on chat_history (session_id);
```

### AI 用户画像接口（2026-09-14 新增）

| 接口 | 权限 | 说明 |
|---|---|---|
| `GET /user/profile/switch` | 登录 | 查「使用 AI 记住的偏好」开关（无画像时返回默认开启） |
| `PUT /user/profile/switch` | 登录 | 改开关。只关「回灌」，不关「后台沉淀」 |
| `GET /admin/user-profile/{userId}` | `user:view` | 画像详情，**无画像时返回带用户基础信息的空结构，不是 404** |
| `GET /admin/user-profile/tags` | `user:view` | 受控标签词表（9 个，筛选下拉用） |
| `GET /admin/user/export` | `user:view` | 按当前筛选条件导出（不分页，上限 2000 行；前端转 CSV） |
| `PUT /admin/user-profile/{userId}` | `user:manage` | 人工修正画像（整份覆盖，允许清空；不能改 user_id 与回灌开关） |
| `PUT /admin/user-profile/{userId}/remark` | `user:manage` | 更新运营备注与标记（独立保存） |

权限点**复用** `user:view` / `user:manage`，没有新增权限点 ——
所以不用去改角色表里的权限串（新增权限点若忘了同步角色表，会表现成菜单不显示、页面被重定向）。

`GET /admin/user` 的分页接口新增两个筛选参数：`profileTag`（受控标签名）、`profileMark`（模糊）；
返回项新增 `profileTags / profileSummary / profileChatRounds / profileUpdateTime / profileSource / profileRemark / profileMark`。
